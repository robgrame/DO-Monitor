# Offline snapshot analysis

Analyzer version: **2.9.8**. Requires Windows PowerShell 5.1 or PowerShell 7.
No Azure connection, modules, credentials or network calls are needed.

`scripts\Analyze-DOLocalSnapshots.ps1` analyzes the collector's `DO-*.json` files
for **one machine**. It returns a PowerShell report object and can save the same
report as JSON. Run elevated to read the protected local collector directory,
or analyze snapshots copied to an authorized analyst location.

## Usage

```powershell
# On the machine, from an elevated PowerShell session:
$Report = .\scripts\Analyze-DOLocalSnapshots.ps1 -Verbose
$Report.Summary
$Report.Traffic
$Report.Policies.LatestKnownBySource

# On an analyst machine; the output directory must already exist:
$Report = .\scripts\Analyze-DOLocalSnapshots.ps1 `
    -InputDirectory 'D:\Collected\PC001' `
    -OutputPath 'D:\Reports\PC001-20261015.json' -Verbose

# Include subdirectories and use a different expected collection interval:
$Report = .\scripts\Analyze-DOLocalSnapshots.ps1 `
    -InputDirectory 'D:\Collected\PC001' -Recurse -ExpectedIntervalMinutes 15

$Report.TopJobsByObservedDownload | Format-Table
$Report.Policies.Changes | Format-Table
$Report.Performance.Summary
$Report.DataQuality

# Full latest details and status history for each observed job:
$Report.Jobs | Select-Object FileId, FirstSeen, LastSeen, ObservationCount, ResetCount
$Report.Jobs[0].LatestJob | Format-List *
$Report.Jobs[0].StatusHistory | Format-Table
```

Inputs are processed by `CollectedAt`, not filesystem modification time or name.
Temporary `.tmp` files and unrelated JSON filenames are excluded. With `-Recurse`,
keep each device in a separate directory tree. A mixed-device/serial-number input,
unsupported schema, conflicting snapshot ID, malformed record, invalid byte
counter or ambiguous equal timestamp causes an explicit error and exit code 1.
No invalid file is silently ignored. Success returns the report and exit code 0.
Keep byte counters as JSON integers, as generated by the collector; floating-point
representations beyond the reader's exact integer range are rejected.

## Report contents

| Section | Contents |
|---|---|
| `Device`, `Summary` | Latest device context, serial, time range, file/unique-snapshot counts, distinct/latest jobs, partial samples and sampling intervals |
| `Traffic` | Deduplicated observed bytes by source/destination, separate first observations and subsequent increments, peer/cache source shares |
| `Jobs` | Each distinct FileId, first/last appearance, observation/reset counts, counters, latest full job fields and status changes |
| `TopJobsByObservedDownload` | Top 10 jobs by deduplicated observed downloaded bytes |
| `JobDistributions` | Unique jobs by latest known status, DownloadMode and caller application |
| `Policies` | Latest raw policies, latest known GPO/MDM/Local values with timestamps, initial baselines, additions/removals/changes |
| `Performance` | Original performance samples, availability and per-numeric-property sample count/min/max/mean/latest |
| `Timeline` | Ordered snapshots, original paths, job counts and current cumulative counters |
| `DataQuality` | Duplicate files, counter resets, sampling gaps and original collection errors |
| `Interpretation` | Accounting and interpretation caveats included in the report itself |

## Correct interpretation of byte statistics

**Do not sum the original cumulative counters across snapshots.** The analyzer
tracks each FileId independently:

1. Its first sample becomes `FirstObservedCounters`.
2. Later increases contribute only their delta to `SubsequentObservedCounters`.
3. A counter decreasing is flagged as a reset and its new value contributes to
   subsequent observed bytes.

`ObservedCounters` is the sum of first observations and subsequent increments.
For example, a job observed at 100, 150 and 30 bytes contributes **180 bytes**
(100 + 50 + 30), not 280. Job disappearance does not reset its baseline; when it
reappears, comparison uses its last observation.

First observations can include downloads that occurred **before the requested
files' time range**. Subsequent increments exclude each job's first observation,
including jobs appearing later in the input. These are observed counters, **not
an exact traffic ledger for the time window**. Missed jobs, resets between samples,
and repeated downloads that return to the same counter cannot be reconstructed.
A decrease can also reflect a counter correction, not necessarily a new download.

Peer-type counters are subdivisions of `BytesFromPeers`; they must not be added
to that total. Percentages use only peers + HTTP + cache-server source bytes as
their denominator, which is separately reported and may differ from the primary
downloaded-byte counter. Upload totals include all four peer destinations.
Empty traffic produces null percentages, not an invented zero efficiency.

## Policies, performance and gaps

Policy baselines are captured at the first successful observation of each source.
The analyzer records additions, changes and removals separately for GPO, MDM and
local configuration. If a source failed during collection, it retains that source's
last known values with the last successful timestamp; absent values in a failed
sample are **not removals**. An empty successful policy source means no values
were configured. The report does **not** infer GPO/MDM precedence or effective policy.

Performance averages are **unweighted sample averages**. Missing/null metrics and
failed performance samples are not counted as zero. Performance cumulative
counters are never added to job traffic.

The default expected interval is five minutes. An actual interval greater than
1.5 times that expectation is listed as a sampling gap; a gap can reflect a
sleeping/offline machine, delayed execution or missing collected files. It does
not prove the exact number of missed jobs or scheduled invocations.

## Output safety and verification

`-OutputPath` is optional. Without it the report remains a PowerShell object.
JSON exports are UTF-8 without BOM, flushed to a unique temporary file and then
renamed. Existing reports are never overwritten, and report names must not match
`DO-*.json` to avoid reading the report as a snapshot in future analyses.

Reports include raw job URLs, device identifiers, source paths and policy values.
Choose an output directory with suitable access control and disk encryption;
exports inherit its permissions. No redaction, upload or automatic retention is
performed. The input snapshots are never modified or deleted.
